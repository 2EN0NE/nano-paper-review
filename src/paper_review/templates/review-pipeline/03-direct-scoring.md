## 评审依据（关键）

- **已知的公开技术标准**对该技术文章问题定义准确性的判断
- **从前面步骤查询到的相似文章对比**（如有）
- **论文中提到的证明材料严谨性，逻辑自洽性**
- **做了且有图片、数据等举证材料**的情况
- **技术解决方案看的关键指标是否提供**

> ⚠ 容错说明：若预检索未找到相似文章（「历史参考」与「本批次」均为空），**不要臆造参考来源**，相关维度基于论文自身内容 + 公开常识评分，并在 rationale 中注明「无相似论文可比对」。

每个维度打分必须引用至少 2 个参考来源作为依据。不打分自吹自擂的内容，要基于实际证据。

## 打分维度

### 维度 1：创新性（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 超越业务需求或部门要求的业务功能或技术特性 |
| 2 分 | 超越业务需求或部门要求，新增或改造基础模块，如公共库、公共模块、公共控件等 |
| 3 分 | 超越业务需求或部门要求，改造基础服务，如新技术应用、架构解耦、性能提升、高可用改造、信息安全提升、软硬件资源节约等 |
| 4 分 | 超越业务需求或部门要求，新建基础服务 |
| 5 分 | 新建行业首发、或虽非首发但有证据证明行业领先的基础服务 |

### 维度 2：质量提升效果（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 修补软件缺陷、信息安全漏洞、生产事件 |
| 2 分 | 通过代码逻辑优化，预防软件缺陷、信息安全漏洞、生产事件 |
| 3 分 | 通过架构改造，减少协调、梳理、相关性分析、代码检视等人力投入能保持软件缺陷、信息安全漏洞、生产事件水平 |
| 4 分 | 通过架构改造、工具化、自动化等技术手段，在低人力投入下能减少软件缺陷、信息安全漏洞、生产事件 |
| 5 分 | 通过架构改造、工具化、自动化等技术手段，在低人力投入下能减少软件缺陷、信息安全漏洞、生产事件，出现后也能自动降低负面影响 |

### 维度 3：效能提升效果（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 可使后续开发按小组织开展 |
| 2 分 | 可使后续开发按小组织、轻流程开展 |
| 3 分 | 可使后续开发按小组织、轻流程、低开发要求开展 |
| 4 分 | 可使后续开发按小组织、轻流程、低开发、低运维要求开展 |
| 5 分 | 可使后续开发按小组织、轻流程、低开发、低运维、低技能要求开展 |

### 维度 4：风险敏感性（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 本次成果如果出现异常，不影响生产运行 |
| 2 分 | 本次成果如果出现异常，影响限于公司内人员 |
| 3 分 | 本次成果如果出现异常，影响外部客户，但限少量业务品种 |
| 4 分 | 本次成果如果出现异常，影响外部客户大量业务品种，但不会有社会影响；或影响公司内高管人员 |
| 5 分 | 本次成果如果出现异常，影响外部客户，会有社会性影响 |

> 此维度基于论文中透露出系统在业务链路中的位置推断。判断依据：业务重要性（资金账务类更重要、离线报表类相对次要除非面向高层决策）、用户类型（内部用户 vs 外部用户，不同用户判重要性规模基准不同）、当前技术部分在业务中的位置。

### 维度 5：难度（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 业务逻辑的实现 |
| 2 分 | 在应用层上对既有架构的完善或封装 |
| 3 分 | 实现系统的架构，或对开源软件、外购软件等他人软件的复杂应用 |
| 4 分 | 架构实现中包含大量直接操作 OS 内核层、硬件驱动层、数据库服务层等相对底层的代码，或解决了部门内他人未曾克服的技术难点 |
| 5 分 | 架构实现中包含大量作为 OS 内核层、硬件驱动、基础算法等底层模块的代码，或解决了行业内他人未曾克服的技术难点 |

### 维度 6：业务价值提升效果（1-5）

| 分数 | 标准 |
|------|------|
| 1 分 | 为业务部门创造政绩，交易或使用量小 |
| 2 分 | 为公司创造市场概念，交易或使用量小 |
| 3 分 | 为公司既有客户提升服务质量、服务体验，且交易或使用量大；或为公司内用户提升工作效能，且交易或使用量大 |
| 4 分 | 为公司创造新业务品种，交易或使用量大；或为公司提升内部管理，在效能、成本、风险、速度、灵活性等方面效果显著 |
| 5 分 | 为公司新增原非公司客户，且新增客户数量大；或直接减少公司内人员，且减少人员数量大 |
